# Design → Brief (Phase 1: Think)

Turn a design into an **agreed brief** that a builder can execute autonomously. You do the thinking *with the dev now* so the builder doesn't guess later. Output = `.briefs/<name>.md` (per the `_TEMPLATE.md`).

**You are NOT building anything here.** No files in `sections/`, `blocks/`, `snippets/`, `src/`. The only file you may write is the brief.

## The spine — settings-first, climb the inheritance ladder

**The settings schema is the spine of the build.** Style is not reconciled against the design in isolation — it is reconciled THROUGH the settings. Once the settings are fixed, the agent's style work becomes deterministic.

**Division of labor (this Think phase):**
- **Agent** reads the design → the **markup + Liquid structure + file split** (snippet / block / section) + **layout / style / spacing** + a *draft* settings **tree** (the canonical structural settings + the content slots visible in the design). This is the agent's main job.
- **Dev** defines the **intent / behavioral** settings — what is merchant-configurable vs fixed (toggles, ranges, optional regions, which value becomes a setting vs a constant). The agent **asks these as questions in the conversation** — it never silently guesses a judgment call (when unsure, ask).
- The agreed result is the brief; the builder implements from it (it does not see "who wrote what").

**When implementing any value, climb to the HIGHEST inheritance available — hardcode is the last rung:**
1. **Setting** — if a setting controls it, bind to it (the merchant-live source).
2. **Theme global** — color → a **scheme role** (`--color-foreground` / `--color-background` / `--color-primary-button-*`; **never a hex**); font-size → a **preset class** (`.h1`–`.h6` / `.mega-title` / `.paragraph` / `.text-subheading` / `.text-body-sm|xs` — responsive `clamp()` vars; **never raw px**); radius / motion → the token (`--border-radius`, `--animation-duration--medium`…).
3. **Mirror convention** — hover / focus / state / internal-spacing copied from the nearest real block. (Verified theme convention: hover borrows a **button scheme role** for the accent — usually `color`, e.g. `--color-primary-button-background`/`-text` — plus the `box-shadow`/`transform`/`opacity` lift family, all gated behind `@media (hover: hover) and (pointer: fine)`.)
4. **Hardcode** — only when 1–3 genuinely don't apply; it **must be noted** in the brief's caveats.

color · spacing · font · hover are the same ladder applied four times. If a color isn't in any scheme, or a section legitimately has no padding group, that's a flagged decision for the dev — not a silent hardcode.

**The ladder has an inverse case it doesn't cover: text ON a scheme-role background.** A hardcoded `color: white` on `background: rgb(var(--color-<role>))` is rung 4 in disguise — it looks safe because the *background* climbed the ladder, but roles flip per scheme. `--color-sale-price` is `#ffffff` in `scheme-inverse`, so white-on-white at **1.00:1** is reachable from shipped defaults alone, and any icon on `currentColor` disappears with the text. No static check sees it — only an L2 render under that scheme. **Derive the foreground instead**, and say which way in the brief:
- accent comes from the **scheme** (no colour setting) → use that scheme's own `var(--color-background)`; a scheme's background always contrasts with that same scheme's roles.
- accent comes from a **merchant colour setting** → pick black or white by the real WCAG ratio: `assign c_black = settings.color | color_contrast: '#000000'`, same for `'#ffffff'`, then compare (Liquid `if` can't take filters, so assign first). `color_contrast` returns the ratio's numerator and **does coerce a colour-setting drop**, though the docs only show string literals.
- **never approximate it with `color_brightness` + a threshold** — that's YIQ on gamma-encoded channels (red 0.299) while WCAG contrast uses linearised luminance (red 0.2126), so red-dominant hues read "dark" to one and "light" to the other (measured: `#FF0000` 4.00:1, `#FF00FF` 3.14:1). **No threshold fixes it** — tuning the cut only ever repairs greys, where the two scales happen to agree.
- emit it as a var with the literal only as a fallback (`color: rgb(var(--x-on-accent, 255 255 255))`) so a missing var degrades instead of vanishing. If the design deliberately wants the lower-contrast choice — white on orange is a near-universal sale-badge convention and may measure under AA — expose an explicit `auto | light | dark` setting rather than letting the block silently overrule the designer.

## Inputs
- The **design**: a Figma link/node (read it via the **figma MCP** — desktop + mobile + all variants), or screenshots/description if MCP is unavailable.
- The **target**: section · block · snippet, and a kebab-case **name**.

## Process

### 1. Read the design (all viewports + variants)
Via the figma MCP, extract:
- **Layout** — full-width vs contained; single-content vs a repeated grid; how many columns desktop/tablet/mobile; carousel vs grid.
- **Items** — the repeated unit → a **theme block** (`blocks/_<name>-<item>.liquid`). Even single-content sections put content in a block.
- **Content fields** per item/section → candidate **settings** (heading, text, image, link, icon, CTA…).
- **Interactions** — carousel, hover, motion → JS / which carousel element.
- **Variants** — what changes across designs (mobile swipe, with/without CTA, light/dark, alt layouts) → settings/modifiers.
- **Spacing (read the numbers, don't eyeball)** — every gap / padding / margin between elements, desktop AND mobile, from the Figma auto-layout / `layout_*` values. These become the **Spacing table** (below) — the #1 source of builder drift is prose spacing, where the builder falls back to the mirror's defaults.
- **Typography (read the textStyle)** — every text node: font-family · weight · font-size · line-height · case · desktop + mobile. These become the **Typography table**.
If the figma MCP isn't connected, ask the dev for the node link or screenshots + the desktop/mobile differences + the exact spacing/type values — don't guess the layout or the numbers.

### 2. Find the closest real section/block to MIRROR
Search `sections/` (and `blocks/`) for the nearest archetype (a grid-of-cards → `icon-boxes`/`media-gallery`; a collection → `featured-collection`; a slideshow → `slideshow`/`_slide`). **Read it.** State which one you'll mirror — the build copies its structure.

### 3. Apply the anatomy → derive the plan
Read the relevant playbook(s) and apply them:
- `.claude/skills/create-liquid-section/PROJECT-ANATOMY.md`
- `.claude/skills/create-liquid-block/BLOCK-ANATOMY.md`
- `.claude/skills/create-liquid-snippet/SNIPPET-ANATOMY.md`

Derive:
- **Create** — `sections/<name>.liquid`, `blocks/_<name>-<item>.liquid`, `src/scss/global/_section-<name>.scss` (+ `_component-…` if shared), new `t:` keys (only if no existing key fits).
- **Reuse** — snippets (`responsive-image`, `button-markup`, `spacing-style`, `border-style`, `gap-style`, `icon-or-image`…) and any existing block types. **Reuse-first**: never reimplement an existing snippet/block. Reuse-first applies to **behaviour** as much as markup — and the brief must prove it: **list every behaviour the design implies** (anything that scrolls, opens, collapses, slides, counts, sticks, animates, zooms…) **and map each one against PROJECT-MAP §0 (Capability index)** — search §0 by behaviour keywords; run `yarn map` if the file is missing. Each behaviour resolves to either the §0 component that serves it (name it + its markup contract) or an explicit **"not in §0 — build new"**. A behaviour with neither is a spec gap the dev must see. The recurring miss is a **horizontal scroll row** — a tab bar, filter pills, a chip row — hand-rolled as `overflow-x: auto` when `.edge__shadows` + `<div is="swipe-component">` already give edge fades and auto-scroll-to-active for free; "it scrolls" is not a spec.
- **Settings schema — a grouped TREE, split by level.** Give the **section** its own tree and each **child block** its own separate tree (never merge a block's settings into the section's). Within each, group by header in canonical order — section: Layout (`container`, `type`, `columns_xxl`, gaps) → Mobile layout → Appearance (`color_scheme`, `border`) → Padding (canonical device block, defaults desktop 0/0 + mobile 48/48); block: Layout → Media → Content → Appearance (canonical ids/defaults from BLOCK-ANATOMY). The agent **drafts** the canonical structural settings + the content slots it sees in the design; the **dev** fills the intent settings (the agent marks those as open questions, doesn't invent them). **Every Figma field maps to a setting OR is flagged hardcoded** (per the inheritance ladder). Reuse existing `t:` keys.

### 4. PROPOSE — don't write the brief yet
Present a concise plan to the dev: **mirror** · **Create** list · **Reuse** list · **grouped settings** · **behavior (grid/carousel + element)** · **variants**. Invite changes. Resolve ambiguities explicitly (grid vs carousel default? which block type? a setting vs a hardcoded value? CTA in which block?).

**Always pin these three for any block/card — they change the schema and the data:**
- **Addability / block shape — dynamic or static?** Is it a **dynamic** theme block (merchant-addable via `@theme` — public name + `presets`, droppable in `custom-section`/`group`/`grid`) or **static / section-scoped** (host-rendered only — internal `_`-prefixed, NO presets, a specific section loops it)? *(This is the public-`@theme`-with-presets vs internal-`_` split from BLOCK-ANATOMY §1 — NOT the "static vs dynamic children" of §4.1.)* Consequence for the schema: **a dynamic block MUST carry the Size/Width group** (`width`/`width_mobile`: fit|fill|custom + `custom_width`/`custom_width_mobile`) and can't assume a parent background (may need its own `background_type`/`color`); a **static** block inherits its host section's width + scheme. The #1 miss is shipping a dynamic block without its width group.
- **Data binding** — where does its data come from: a **merchant picker** in the block (e.g. a `collection`/`product` `*_picker` setting) or **contextual** (`closest.collection`, `closest.product`)? Host-rendered cards use `closest.*`; standalone merchant-added cards need their own picker. State which, so the brief doesn't ship a card with an empty title because it assumed a context that isn't there. ⚠️ **`closest.product` (and `closest.*`) is BLANK inside a generic `custom-section`** — even on a product template — because it only resolves in a section that carries product context, not a generic content section. So a block a merchant drops into `custom-section` on a product page must use a **3-step chain**: `block.settings.product` (own picker) → `closest.product` → the **global `product`** object (the template's current product). A 2-step `settings.product → closest.product` alone renders empty until a product is manually picked.
- **Shared setting groups** — tick which of the recurring groups this block needs, so the tree is complete (a missed group = a control the merchant can't reach): **Padding** (device block + `mobile-padding-scale`; near-universal) · **Appearance/color** (inherit `color_scheme` `+ inherit_color_scheme` | own `background_type` scheme|gradient | `color`/`icon_color` override) · **Size/dimensions** (width group for dynamic blocks; `height`/`aspect_ratio` for media) · **Border** (`border` toggle/width/color + `border_radius`) · **Animation** (`animation_type` + `animation_delay`, gated `visible_if settings.animations_enabled`) · **Margin** (only where padding can't apply, e.g. around a `.btn`) · **Typography** (`type_preset`/font for text-bearing blocks).

**For a REPEATED-ITEM feature (gallery / list / carousel / media wall), also pin these — each one flip-flops mid-build if left open:**
- **Item SOURCE** — where does the list of items come from? (a) **nested child blocks** the merchant adds (`content_for 'blocks'`), (b) a **product/collection metafield** (the one core mirror is `foxtheme.collection_megamenu_image` — see `blocks/_mega-menu-sidebar.liquid`), (c) a **native resource** (`product.media`, `collection.products`), or a **priority** between them. This decides whether you even need a child block + split-marker or just a Liquid loop. Swapping the source later is a near-total rewrite of the item path.
- **PER-ITEM vs CONTAINER-WIDE data** — does ONE binding (product/color/link) apply to the whole gallery, or does **each item carry its own**? ("Videos for THIS product" = one product; a home-page "shoppable wall" = a different product per item → the picker moves onto the child, not the parent.) This decides where the data picker lives.
- **MEDIA TYPES** — image only, video only, or **both**? "Media gallery" implies both → an image child AND a video child (or a `media_type` switch), and the modal/slide must handle each (a video slide has a player + controls; an image slide is static). Adding the second type later means a new child block + markup + modal branch + a rename.
- **HOST SCOPING — one section or many?** A **public** block (presets, no `_`) appears via `@theme` in EVERY section that accepts it — so a PDP block and a custom-section block of the same public type BOTH show up in product-information (duplicate). To scope a block to ONE host, make it **private (`_`-prefix) + whitelist its type** in the host's `blocks` array — the host can be a section OR a block (mirror: `_promotion-alert` whitelisted in `blocks/_product-details.liquid`, `_marquee` in `sections/custom-section.liquid`). That whitelist is a **core-file edit** (non-additive — flag it in the brief's caveats). If the two contexts need different settings/data, ship **two private blocks sharing one markup**, each whitelisted in its own host — not one public block.

### 5. Converge → write the brief
On agreement, write `.briefs/<name>.md` from `.briefs/_TEMPLATE.md`, filled with the agreed plan. Six outputs are **MANDATORY** (the builder executes blind, and the testers only verify what the brief pins — a value not in the brief is a value the builder guesses AND nobody tests). Scope: for a brief with **no Figma**, the Spacing/Typography tables may be "N/A — no design; all values bind to tokens/mirror" (L2 then skips measurement); the **Interactions and Edge-cases tables may never be omitted** — an explicit "N/A — <why>" is their only allowed empty state:
- **Spacing table** — one row per gap/padding/margin: *element → element · desktop · mobile · Figma ref*. No prose-only spacing ("a tick list under the heading" is not a number). Bind each row to a setting/token where one exists; L2 asserts token-bound rows by class presence and literal rows by measured px.
- **Typography table** — one row per text: *element · font-family · weight · font-size · line-height · case · desktop+mobile · Figma textStyle ref*. Same binding rule.
- **Settings inspector preview** — an ASCII mock of the Theme Editor inspector for each settings box (section + each child block), drawn from the agreed tree: group by `header`, one row per setting with its control type, conditional rows flagged "← only if …". Lets the dev eyeball the whole schema at a glance before building. (Format + legend in `_TEMPLATE.md`.)
- **Interactions table** — one row per behavior: *element · action · expected*. This IS L2's interaction test plan (Mức C) — a behavior not listed is a behavior nobody tests. A static feature writes **"N/A — static, no interactive element"** explicitly; absence-by-omission is not allowed.
- **Edge cases table** — walk `_TEMPLATE.md`'s checklist (long content, max items, empty data, blank image, sold-out/on-sale for commerce) WITH the dev, one decision per row; rows that don't apply get an explicit "N/A — <why>". L2 renders its stress/empty fixture instances from these rows.
- **Evidence log** — one row per *external or environmental* factual claim the brief relies on: *claim · status (✅ verified / ⚠️ assumed) · how it was checked (file:line, doc name, or "tested in browser")*. Codebase facts cite `path:line`; API/platform facts cite the primary doc, never a blog or a memory; anything untestable in-session is ⚠️ with the builder's cheapest confirmation step named. **Any load-bearing ⚠️ row — one whose falsity would change the architecture — must also carry a STOP instruction** telling the builder to re-confirm it before writing code and report back if it does not hold. If an earlier draft of the brief asserted something later found false, keep a short *"corrections applied — do not reintroduce"* list underneath; a brief is edited across a conversation and a corrected claim otherwise reappears from the dev's memory of the earlier draft.

Bind each value to the highest inheritance rung (a preset class / a setting / a token) where one exists; only the genuinely design-specific numbers are literal — and those are exactly what these tables pin. Confirm it's saved and tell the dev the next step: `/build-batch <type>:<name>` (or several at once), or `/ship-batch` for the autonomous build→test→fix loop.

## Principles (don't drift)
- **Settings are the spine; climb the inheritance ladder** — every value takes the highest-inheritance source (setting → theme global → mirror → hardcode-LAST). Color → scheme role never hex; font → preset class never px; hover → scheme role + lift. A hardcode is flagged in the brief, never silent (see "The spine").
- **Ask, don't guess** — the agent fills what's deterministic (structure, style, canonical settings) and **asks the dev** the intent/judgment settings; an unsure call becomes a question, not a filled-in guess.
- **Verify, don't recall** — "Ask, don't guess" governs *judgment*; this governs *fact*. Every factual claim that reaches the brief — what a third-party API accepts or costs, what a CSS/browser mechanism does, a theme token's value, whether a `t:` key or snippet already exists, what a mirror file actually contains — must be **checked at Think time**, not recalled. A grep, a doc fetch, or a 2-minute browser test is always cheaper than a builder implementing a confident falsehood and L2 measuring it as correct. Recall is a hypothesis; the brief may only carry verified facts, explicitly-flagged assumptions, and agreed decisions. **The tell that you are recalling: you can state the claim but not name where you'd check it.** If a claim can't be verified in the session, it does not become a flat assertion — it becomes a row in the Evidence log marked ⚠️ with the cheapest way for the builder to confirm it first.
- **Intent isn't a fact — ask the designer.** The two rules above both assume the answer is reachable: the dev can decide it, or a grep/doc/test can settle it. A question about *why the design is the way it is* is neither, and "Verify, don't recall" misfires on it — the design file is the primary source, so re-reading it feels like verifying while it can only ever hand back the same artifact. Anything that looks like an inconsistency **between** views (desktop and mobile disagree, one instance of a repeated element differs, a value matching no token and no other node) is an **unanswered question**, not something to resolve by examination. Examining harder makes it worse: a slip repeated across several nodes is indistinguishable from a deliberate choice, and the second look tends to produce confidence rather than accuracy. Observed: a 6px radius present on mobile and absent on desktop was called a slip, then — after a closer look found it applied coherently across four corner nodes — confidently retracted as deliberate, with a plausible responsive rationale. One question to the designer: it was a slip. Route it as one line, and record the answer in the Evidence log with **who** confirmed it and **when**. If it can't be asked in the session, the brief carries BOTH readings, an explicit ⚠️, and a note that the builder and the L2-vs-Figma pass will each flag it — otherwise one unasked question becomes two downstream false positives.
- **Section is a layout container** — buttons/images/icons live in the **block**, never at section level (PROJECT-ANATOMY). Every section uses blocks.
- **Mirror real code**, not generic Shopify — the closest existing section is the source of truth.
- **Reuse before create** — propose new files only for what genuinely doesn't exist. **But before listing an existing block/snippet for reuse, open it and confirm it is usable in the role you're giving it** — existing ≠ usable. For a block you intend a **merchant** to add (a `blocks: [{ "type": … }]` whitelist, or anything reachable from `content_for 'blocks'`), check two things in its schema: (1) it has a **setting for the content it is supposed to carry** — some blocks take their text from a `content_for 'block', … text: …` **render parameter** instead, and through `content_for 'blocks'` that parameter does not exist, so they render blank with no field to type into; (2) it has **`presets`** — a preset-less `_`-block is static-placed by a host and was never meant to be merchant-added. A block failing either check ships as a picker entry that is permanently empty, which no `yarn check-*` can see. Name the setting you verified in the brief, so the builder can re-confirm rather than re-derive.
- **Reuse vs modify depends on repo role** — In **core**, reuse = compose: `render`/`content_for` an existing snippet/block as-is; don't edit it to fit a new feature — create a NEW additive file (feature branches are additive-only, `check-additive-feature.sh`). In a **child fork** (a real theme with its own design), **modifying an existing component's visual is first-class** — re-skinning `collection-card` for the new design is the job, not bloat-by-duplication. The split, either way: change **visual** freely (its SCSS `_component-*`/`_block-*`/`_section-*` + markup/classes in the `.liquid` or `-markup` snippet) — sync keeps the child's version; never touch the **contract/logic** (`src/js/modules`, `ref`/`data-*`, `{% liquid %}` data wiring, SCSS manifests) — those stay core's, applied on sync. So a **child** brief MAY say "re-skin `collection-card-markup` to the new design"; a **core** brief says "new `category-card-markup`, composing the same snippets".
- **Capture desktop AND mobile** — they differ; the brief must say how.
- **Don't over-spec** — only the settings the design actually needs; richer demo values go in the preset, not setting defaults.

- [ ] Style resolved by the **inheritance ladder** — colors = scheme roles (no hex), fonts = preset classes (no px), hover = scheme role + lift; every hardcode noted in caveats
- [ ] For any block/card: **addability** (presets vs host-rendered `_`-block) and **data binding** (own picker vs `closest.*`) pinned
- [ ] **Block shape + shared groups pinned** — dynamic (theme block → Size/Width group + own background) vs static (section-scoped); recurring groups (padding/appearance/size/border/animation/margin/typography) ticked consciously

- [ ] **Spacing table + Typography table filled from Figma** (exact desktop+mobile numbers — no prose-only spacing/fonts)
- [ ] **Settings inspector preview** drawn from the agreed settings tree (grouped, per control type, `visible_if` rows flagged)
